# Phase 0 And P1.1 Trust Repair Design

日期：2026-05-17
状态：已确认，等待进入实现计划

## 背景

`AI_Industry_Terminal_Prompt.md` 描述的是完整产品级终端，仓库中已有路线图把它拆成多个阶段。当前用户选择先推进路线图方案 A：先完成 Phase 0 分支收尾，再做 Phase 1 中的 P1.1 写死字符串修复。

当前分支 `codex/homepage-reading-guidance` 已有大量未提交变更，本轮工作需要在不回滚现有改动的前提下，让分支更接近可验证状态，并消除最明显的占位感文案。

## 目标

本轮目标是完成一个小而可验证的信任修复切片：

- 保留并验证 `/map` 路由和 `MapPage.tsx`，避免分支收尾时出现路由断裂。
- 修复 roadmap 点名的写死字符串，使公司页和产业层页的关键说明来自真实上下文。
- 运行聚焦测试和生产构建，记录任何仍需后续阶段处理的问题。

## 选择的方案

采用保守的局部修复方案：

- Phase 0 只处理会阻塞当前分支验证的问题，不清理所有历史未提交文件。
- P1.1 只修复明显占位或硬编码文案，不引入完整 glossary 字典。
- 若发现构建失败来自现有未完成改动，优先修复与本轮范围直接相关的问题；不相关的大问题记录为后续项。

这个方案比直接推进完整 Phase 1 更稳，因为当前工作树已经承载了多个功能线。第一步先把最容易伤害读者信任的硬编码文案拿掉，同时获得一组新鲜验证结果。

## Phase 0 收尾范围

### `/map` 路由

确认 `App.tsx`、`AppShell.tsx` 和页面文件对 `/map` 的引用一致。当前产品规格仍要求 `/map` 作为全产业链关系网络图存在，因此默认保留该路由和 `MapPage.tsx`。

如果 git 状态曾显示 `MapPage.tsx` 被删除，但工作树中仍存在文件，则本轮不删除它；后续提交应包含保留后的文件状态。

### 验证命令

本轮至少运行：

- `npm test -- src/App.test.tsx --run`
- `npx vitest run src/data/__tests__/catalog.test.ts`
- `npm run build`

如果这些命令暴露与 P1.1 无关的失败，需要在结果中说明失败原因和归属，不把未经验证的状态称为完成。

## P1.1 写死字符串修复范围

### 公司页定位文案

`CompanyPage` 中现有 `positioningItems` 不应再出现对所有公司都相同的 `"为什么属于能源"` 之类硬编码标题。

新的行为：

- 从 `company.aiBusiness.layerIds[0]` 找到首个产业层。
- 用该层的 `layer.name.zh` 生成标题，例如 `为什么属于芯片设计`。
- 如果公司没有产业层或数据缺失，使用克制的兜底标题 `产业链定位`。
- 文案内容仍可复用现有公司与层级字段，不额外编造新事实。

### 产业层技术组成说明

`LayerPage` 中 `"该能力节点用于演示本层技术组成。"` 这种占位句需要替换为真实上下文说明。

新的行为：

- 优先使用一个本地 helper，根据技术术语和当前产业层生成一句定义性说明。
- 说明应体现“该技术在当前产业层中的作用”，不能再出现“演示”“占位”“mock 展示”这类半成品字眼。
- 本轮不要求覆盖完整 glossary，不新增全局 tooltip 体系。

### 占位文案扫描

本轮以 `src/pages/CompanyPage.tsx`、`src/pages/LayerPage.tsx` 和相关测试为主，使用 `rg "演示|为什么属于能源"` 确认点名问题消失。

如果其他页面仍有合法的 demo data 标注，不纳入本轮清理；示意数据声明是产品信任要求，不应删除。

## 不在本次范围

- P1.3 每条指标来源体系。
- P1.4 Relationship hover 叙述。

- Phase 3 adapter hook 接通。
- 重写视觉风格或引入新的 3D 转场系统。
- 清理所有未提交历史变更。

## 测试与验收

本轮完成后需要满足：

- `/map` 路由仍在 `AppRoutes` 中，导航仍能指向 `/map`。
- `CompanyPage` 不再为所有公司显示固定的 `"为什么属于能源"`。
- `LayerPage` 不再显示 `"该能力节点用于演示本层技术组成。"`。
- 聚焦测试能覆盖至少一个公司页层级定位标题和一个产业层技术说明。
- `npm run build` 给出新鲜结果。

如果现有工作树中的其它未完成事项导致全量验证失败，需要报告失败命令、关键错误和建议下一步，而不是扩大本轮范围盲修。
